# 🛡️ AI-Powered Fraud Detection System

A real-time payment fraud detection prototype built with **Random Forest** + **Isolation Forest**, featuring a customer-context layer that reduces false alerts for genuine customers.

> **Hackathon Note:** Built using PaySim (synthetic data). The "real-time" simulation is a demo — not Kafka/streaming. See [Limitations](#limitations).

---

## 📐 Architecture

```
PaySim CSV
    │
    ▼
train_model.py ──────────────────────────────────────────────────────────
│  • Stratified sample (all fraud + legit sample, max 300 k rows)       │
│  • Chronological split on `step` (80/20)                               │
│  • RandomForestClassifier (class_weight="balanced_subsample")          │
│  • IsolationForest (trained on legit rows only)                        │
│  • Saves: fraud_model.pkl, anomaly_model.pkl, config.pkl               │
└────────────────────────────────────────────────────────────────────────

fraud_engine.py (inference)
    │
    ├─ Build feature row  (one-hot `type`, reindex to saved columns)
    ├─ RF  → fraud_probability
    ├─ ISO → anomaly_score, is_anomaly
    ├─ Customer-context layer (normal_customer_pattern flag)
    └─ 4-Tier Decision Engine
           ├─ ≥ 80% prob         → HIGH RISK  (context CANNOT override)
           ├─ ≥ 30% prob OR anom → MEDIUM RISK (unless context clears it)
           ├─ Context clears it  → LOW RISK - CONTEXT MATCH
           └─ All clear          → LOW RISK

app.py (Streamlit UI)
    ├─ Dashboard     — metrics, pie/line charts, transaction log
    ├─ Test Transaction — manual scorer with gauge chart
    └─ Live Simulation  — random batch scoring with live bar chart
```

## 🔑 Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| **No `newbalanceOrig`/`newbalanceDest`** | Prevents data leakage — these reveal the transaction outcome |
| **Chronological split** | Simulates real deployment: model never trained on future data |
| **`class_weight="balanced_subsample"`** | Handles extreme class imbalance (~99.8% legit) without over-sampling |
| **IsolationForest on legit-only** | Learns what "normal" looks like; detects novel fraud patterns RF might miss |
| **Customer-context layer** | Reduces false positives for genuine customers — LOW RISK - CONTEXT MATCH tier |
| **Precision-recall threshold** | Chosen to maximize precision while keeping recall ≥ 0.85 |

## ⚠️ Limitations

- **PaySim is synthetic.** It's generated by an agent-based simulation tool. Real fraud is messier, non-stationary, and adversarial.
- **"Real-time" is simulated.** There's no Kafka, Flink, or streaming infrastructure. Live Simulation uses `time.sleep()` between scored rows.
- **Customer context is offline.** `customer_avg_amount` is derived from training data, not a live feature store. In production this requires a real-time customer profile service.
- **No concept drift detection.** Fraud patterns evolve; the model would need periodic retraining.
- **Single-machine, in-memory.** Not designed for horizontal scaling.

## 💡 Judge Q&A

**Q: Why Random Forest?**  
A: RF handles high class imbalance well (via `balanced_subsample`), is robust to correlated features, produces calibrated probabilities, and is interpretable via feature importance. Training time is acceptable on 300 k rows.

**Q: Why Isolation Forest?**  
A: RF learns from labeled examples — IsolationForest catches *novel* fraud patterns that look statistically unusual even if they don't match known fraud signatures. The dual-model approach improves recall.

**Q: How do you reduce false positives?**  
A: The customer-context layer checks whether a transaction fits the customer's historical behaviour. If the amount is within 1.5× of their typical amount *and* the pattern is familiar, a borderline MEDIUM-RISK transaction is downgraded to LOW RISK - CONTEXT MATCH — avoiding a friction-causing alert.

**Q: Is it real-time?**  
A: The inference engine (`predict_transaction`) is single-row, sub-millisecond on CPU. The "Live Simulation" in the app is a demo of this speed, not a production streaming pipeline. A production deployment would add a Kafka consumer feeding rows to this engine.

**Q: What's the main limitation?**  
A: PaySim is synthetic and stationary — real fraud is adversarial and drifts over time. A production system needs continuous retraining, concept drift detection, and adversarial testing.
